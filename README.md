# 心动菜单 · 情侣点菜微信小程序

一餐两人，刚好是我们。帮助两位用户各自选菜，找到共同想吃的那一口。

交付包含**原生微信小程序（WXML / WXSS / JavaScript）**、可持久化的 Node.js 双人同步服务、Cloudflare Workers 部署入口，以及便于电脑查看的响应式浏览器预览。小程序使用原生页面，没有使用 web-view 包装网页。

## 已实现

- **面对面点菜**：同一台设备轻点头像切换两人的身份，各自标记想吃或不想吃；再次点击可撤销。
- **远程同步**：创建双人餐桌，用微信分享卡片或 8 位邀请码邀请另一半；两端通过长轮询即时获取变更，断线自动重连。服务端限制每个房间两位成员，远程模式不能修改另一位的选择。
- **双向心动**：两人都想吃的菜自动高亮，并汇集到共同喜欢区域。
- **随机推荐**：优先共同喜欢，其次任意一方喜欢，最后从未被拒绝的菜中选择。任意一方不想吃的菜都不会被推荐；所有菜都被拒绝时提示调整选择。
- **轮流决定**：记录当前决定者，确认一餐后自动换人；远程模式只允许当前决定者完成决定。点击共同菜品可直接决定，随机候选支持再换一道。
- **私房菜单**：添加、编辑、删除自定义菜品，设置图标、名称、描述、辣度、荤素和分类，价格固定为 0 元；对方同步可见。
- **筛选与收藏**：关键词、分类、辣度、荤素、价格可组合筛选；两人的收藏各自独立。
- **我们的食光**：确认结果后保存菜品快照、决定方式和时间，支持再吃一次；新一轮只清空选择，保留菜品、收藏和历史。
- **粉色心动界面**：按提供的设计图实现心动菜单、Hello Kitty 厨房横幅、专属留言、横滑分类、横向菜品卡片、固定底栏与心动订单。桌面双列、手机单列，支持悬停、展开、切换、滚动、加载和错误反馈。32 道默认菜品全部使用独立生成的对应图片，所有默认菜与自定义菜均为 0 元。
- **共享已选与订单**：点加号加入两人共享餐篮，可增减份数和填写备注；提交后生成订单、清空已选。右上角厨师按钮进入厨房，按已接单 → 准备中 → 制作中 → 可以开饭更新进度，另一端自动同步。
- **删除订单**：普通订单页和厨房内均可点击每张订单右上角的「删除」。确认后从两人的记录中同步移除，取消则保留；支持制作中、已完成及旧版历史订单，删除后无法恢复。

## 本地启动

Windows 推荐双击工程根目录的 **启动网页.cmd**。它会启动独立的后台预览进程并打开网页，重复点击会复用已有服务。也可以执行 `node scripts/start-preview.js` 或 `npm run preview`。关闭启动窗口不影响该进程；电脑重启后需要再次启动。服务日志在 `artifacts/preview-service.log`。

`localhost:3000` 仅代表当前电脑，不能作为手机或其他设备的公开访问地址。远程访问配置见下文。

需要 Node.js 20 或更新版本。运行后端和浏览器预览**不需要安装第三方依赖**。

```powershell
cd D:\iwen-codex\codex-menu
node server/index.js
```

浏览器打开 [http://localhost:3000](http://localhost:3000)。可在两个独立浏览器或无痕窗口中通过邀请链接验证远程模式；同一浏览器共享本地设备身份，适合验证面对面模式。

默认监听 `0.0.0.0:3000`。可用环境变量 `PORT` 修改端口，`DATA_DIR` 修改数据目录。已有服务占用 3000 端口时，可使用：

```powershell
$env:PORT = '3001'
node server/index.js
```

## 导入微信开发者工具

1. 在微信开发者工具中导入**整个工程根目录**，即包含 `project.config.json` 的文件夹。
2. 填入自己的小程序 AppID 或开发者工具认可的测试 AppID。工程目前使用 `touristappid` 占位，没有绑定任何真实账号。
3. 确认小程序目录为 `miniprogram/`。
4. 启动上面的 Node 服务。`miniprogram/config.js` 默认指向 `http://127.0.0.1:3000`，供同一台电脑的开发者工具调试。
5. 本地调试时，项目设置暂时关闭合法域名校验。点击编译即可浏览页面、面对面选菜、收藏、管理菜品和查看记录。

**真机和远程使用**：将 Node 服务部署到公开可访问的 HTTPS 域名，把 `miniprogram/config.js` 的 `apiBase` 改成该域名，并在小程序后台将其配置为 request 合法域名。手机上的 `127.0.0.1` 指向手机自身，不能用于访问电脑上的服务。

填写 AppID 后，在邀请弹层中使用原生 `open-type="share"` 按钮发送小程序卡片。接收端通过 `pages/index/index?room=邀请码` 加入同一餐桌。当前工程没有微信 AppSecret，也不需要将任何服务端密钥放进前端。

## 使用流程

**点菜**：点菜品图片或名称展开详情，标记「想吃 / 不想吃」；爱心收藏，加号加入已选。选择「已选」调整份数、填写备注并提交。

**面对面**：默认进入面对面模式 → 在「我们」页切换头像 → 双方分别选择 → 双向心动自动高亮 → 可以直接确认或加入餐篮。

**远程**：在「我们」页点「邀请另一半」 → 房间切换到远程模式 → 分享小程序卡片或邀请码 → 对方加入 → 各自在自己的设备上选菜。

**还没有共同选择**：匹配区域提供随机推荐与轮流决定入口。随机推荐不会自动保存一餐，只有点击「就吃它，开饭啦」才生成历史记录。

「我们 → 我们的昵称」可设置昵称、加入已有餐桌或创建新餐桌。房主可开始新一轮，也可切回面对面模式。右上角厨师按钮进入厨房管理订单，再点一次返回普通订单视图。

制作时间为估算值，爱心表示制作难度。订单只在用户提交或确认推荐后产生；初次使用显示空订单，不插入示例订单。

## 开发与验证

正式运行无需安装依赖。修改代码后要运行完整检查时，先安装开发依赖：

```powershell
npm install
npm test
npm run check:mini
npm run test:e2e
```

也可使用 pnpm 按仓库内 `pnpm-lock.yaml` 安装：`pnpm install --frozen-lockfile`。

- `npm test`：28 项检查，覆盖原生页面逻辑、编译后模板分支、双人权限、长轮询、匹配和随机算法、收藏、菜品校验、订单删除、过期确认、轮流决定、持久化恢复和资源体积。
- `npm run check:mini`：使用微信 `wcc / wcsc` 的 Node 封装编译 WXML 和 WXSS，产物在 `artifacts/`。
- `npm run test:e2e`：15 项浏览器流程检查，含两个隔离浏览器间的实际同步，以及 320 / 360 / 390 / 430 / 768 / 1024 / 1440 像素宽度检查。脚本默认使用已安装的 Microsoft Edge；可通过 `BROWSER_CHANNEL=chrome` 改为 Chrome。
- `npm run qa:native`：将真实 WXML 编译树生成可视化检查截图，覆盖菜单、邀请、添加菜品、推荐、订单、已选与我们页面。截图是编译模板的浏览器渲染，**不是微信真机截图**。

原生编译检查与浏览器集成测试已经执行。当前环境没有微信开发者工具及绑定的 AppID，**尚未完成微信真机调试、账号侧分享验证或提交审核**。

## 服务与数据

Node 服务使用 HTTP JSON API 和 20 秒长轮询。选择发生变更时立即唤醒等待的请求，并返回递增版本号；两端忽略旧版本，切换房间时取消旧轮询。请求超时为 30 秒，重连间隔为 2.5 秒。在线状态由最近 45 秒的请求活动估算。

数据保存于 `.data/rooms.json`，采用临时文件替换，服务重启后会恢复。该目录被 Git 和发布包排除。默认保留每房间最近 200 次历史与 200 份订单、最多 100 道私房菜。已选每道菜最多 9 份，一餐最多 50 份。订单进度按顺序推进，重复下单和过期状态更新会被拒绝。

已有部署需要补齐这次新增的中餐时，先停止服务，再运行 `node scripts/sync-chinese-menu.js`，然后重新启动。脚本会备份数据、补齐并前置 20 道常见中餐、将价格保持为 0 元，同时保留双方选择、收藏和历史；重复运行不会重复添加菜品。

已有房间更新图片时，先停止服务，运行 `node scripts/sync-menu-images.js` 再启动。脚本自动备份，只更新内置菜图路径，保留菜名、价格、双方选择、收藏和历史。

当前身份采用随机设备标识与房间令牌，**未接入微信账号登录**。同一设备缓存保留时可以恢复房间身份；清除缓存后属于新设备，若旧房间已经满员，需要建立新餐桌。不要公开私人房间邀请码。

这是适合原型和小规模使用的单进程服务。部署时需持久化数据目录；不要让多个服务实例同时写同一个 JSON 文件。扩展为多实例时，应迁移数据库，并实现跨实例消息通知。

## 部署到 Cloudflare Workers

Cloudflare 上使用 Workers 同时托管页面和 `/api`，房间、双方选择与订单保存在 SQLite Durable Object 中，服务重新发布后仍可恢复。仓库已包含构建脚本、静态资源配置、Worker API 和首次迁移配置。

在 Cloudflare 的 Git 构建设置中选择 **Workers** 项目，生产分支填 `main`，根目录保留 `/`，构建命令填 `pnpm run build`，部署命令填 `pnpm exec wrangler deploy`。不要填写 Pages 的输出目录。完整步骤、验证方式和失败排查见 [Cloudflare 部署说明](docs/CLOUDFLARE.md)。

本地可先执行：

```powershell
pnpm install --frozen-lockfile
pnpm run check:cloudflare
pnpm run dev:cloudflare
```

打开部署域名的 `/api/health`，看到 `{"ok":true,"runtime":"cloudflare-workers"}` 即表示页面和 API 已同时部署。若之前创建的是 Pages 项目，需要新建 Workers 项目后再导入本仓库。

仓库同时包含 `functions/api/[[path]].js`，用于让现有的 `codex-menu.pages.dev` 项目把同源 `/api` 请求转发给 Worker。这样浏览器只需访问 Pages 域名，也不会把缺失的静态回退页面误当作 API JSON。

## 使用 Docker 部署 Node 服务

工程提供 `Dockerfile`、`compose.yaml` 和 `deploy/nginx.example.conf`。以下操作未在当前环境实际部署。

```sh
docker compose up -d --build
```

容器内部监听 3000，Compose 将端口绑定至主机 `127.0.0.1:3000`，交由 HTTPS 反向代理对外提供服务；命名卷保存房间数据。Nginx 示例需填入真实域名和证书路径，并保留大于 20 秒的请求读取超时。部署后检查 `/api/health` 返回 `{"ok":true}`。

发布前填写真实 AppID、配置 HTTPS request 合法域名，并将 `project.config.json` 中的 `urlCheck` 改为 `true`，然后在两台真机上检查邀请、同步、切后台、断网重连和确认记录，再上传审核。

## 工程结构

```text
miniprogram/              原生微信小程序
  pages/index/           页面、原生模板和样式
  utils/model.js         双端共享菜单、筛选与推荐逻辑
  assets/                插画、导航图标和本地菜品照片
  config.js              服务地址
server/index.js          双人房间 API 与持久化同步服务
cloudflare/              Cloudflare Worker API 与 Durable Object
public/                  响应式浏览器预览
tests/                   逻辑、API 与编译模板测试
scripts/                 资源生成、浏览器测试和截图脚本
deploy/                  HTTPS 反向代理示例
wrangler.jsonc           Cloudflare 静态资源、绑定与迁移配置
project.config.json      微信开发者工具导入配置
```

图片与生成说明见 [素材说明](docs/ASSETS.md)，统一视觉提示词和每道菜的素材映射见 [图片清单](docs/food-image-prompts.json)。厨房横幅和 32 道菜图由内置 image_gen 分别生成，并已压缩存入项目；不依赖外部图片网站。
